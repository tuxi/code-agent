# Manual Collaboration V1 生产化需求

日期：2026-11-03。状态：需求已认可，分批实施与验收中；不代表已通过上线验收。

## 目标与范围

让用户在项目中直接委派 Code-Agent，由 Talkify 展示执行和审批，执行期间 Codex 无需陪跑，用户返回后通过一次精简交接恢复审查。协作连接故障不得阻断普通 Codex 对话。

本版围绕既有 MCP、Session、准入回执、EventStore、执行证据和 Handoff 改进，不新增调度器或第二套任务协议。Manual Collaboration 不强制创建 Task；用户需要父任务记录时复用既有 Task 关联。

上线底线：不误派工作区、不重复执行、不绕过审批、不把未验证当通过、不因协作故障阻断普通聊天。

不在本版：Flux/Managed 编排扩展、未知副作用自动恢复、force-resume、第三方 Agent Adapter、自动模型路由、自动唤醒 Codex、通用 Token 网关，以及完整的权限管理 UI。既有 Managed 安全准入和 G1/G3 验收门槛保持独立，不以本版替代。

## 用户主流程

1. 用户一次配置项目 MCP 连接；没有执行任务时无需维护一个固定 Session。
2. Codex 核对连接和授权范围，显式创建或选择本次任务的工作区/Session，并记录原基线。
3. Codex 提交任务、验收要求和验证约定，使用稳定 request_id。
4. 收到持久准入回执后，Codex 告知用户 Session/Turn 和观察入口，立即结束回复；不轮询、不安排自动唤醒。
5. Code-Agent 在原 Daemon 独立执行；用户在 Talkify 观察并处理单次审批。
6. 用户回来要求审查。已知任务身份时，首个业务读取只需一次 Handoff；连接/授权失效时先报告故障，不假装恢复成功。
7. Codex 核查证据及风险；真实问题使用同 Session、新 request_id 返工。无缺陷直接通过，不人为制造返工。
8. 完成提交/合并后，保留历史及审查产物；新任务建立新执行绑定，旧基线不可被改写为当前 HEAD。

## R1 服务连接与任务绑定分离

### 必须行为

- 长期 MCP 配置描述服务入口、连接凭据来源及工具模式，不要求携带某个历史 Session/任务的基线。
- 区分 MCP 传输已连接、Runtime 已授权、执行目标已绑定；前者不能被解释为已获执行权限。
- 无有效授权时可提供不含敏感信息的连接诊断；不得列举私有 Session、读取产物或执行任务。支持在恢复授权后重试，不必重写项目配置。
- 每次委派均确定唯一目标。并行工具调用、另一个聊天的绑定操作、重连或迟到响应不得改变已经提交请求的目标。
- 目标约束至少覆盖规范化工作区及 Git 身份、Runtime/Store、Session、原基线和授权作用域。服务入口改变或身份不匹配时停止，不静默重绑定。
- 新授权只在身份核对后接续原绑定；不得自动续期、扩大授权或将一个项目的 owner grant 当作任意工作区委派许可。
- 支持旧的显式固定 Session CLI 接入；其原有安全约束不降低。旧任务交付后允许保留只读审查，禁止以改基线方式继续写入。
- 不自动迁移现有配置，不自动创建 Session、启动 Daemon或派发任务。

### 验收

- 连续完成两个不同任务，无需修改长期 MCP 启动配置，原任务历史仍可定位。
- 未绑定目标发送、工作区替换/符号链接重定向、Store 切换、并发绑定竞争和越权目标均被拒绝，且没有 Turn 准入或文件写入。
- 授权过期后恢复原范围授权，可以重新核对并继续读取原任务；未知副作用不重放，审批不自动恢复。

### 设计决策门槛

实施前先评审执行目标的显式传递方式，以及是否需要最小的绑定入口。优先复用现有工具；如需改变 schema 或增加入口，必须单独说明必要性、并发语义和兼容策略，不能依赖可被其他调用覆盖的隐式全局“当前任务”。

## R2 MCP 故障不阻塞普通对话

- Codex 配置显式 `required = false`；服务仍可启用。禁用和不可用必须区分。
- Runtime 停止、授权失效、连接超时或旧任务基线变化时，普通对话能够开始并发送；协作操作明确失败，不回退为无授权执行。
- 配置生成/迁移指引保留用户设置，替换同名 server 的旧 required 值，不能重复键或保留另一个必需的旧条目。
- 使用标准 MCP initialize、tools/list 和 tools/call，不污染 stdout，不要求临时 stdio 驱动或 PTY。
- `required` 是客户端配置，不宣称它是跨客户端 MCP 协议。其他客户端使用其原生可选服务机制。

验收：实际 Codex 桌面在服务未运行、授权过期、绑定失效三种情况下均能发送普通消息；恢复后原生工具可用，无需删除项目或聊天。CLI 测试不能代替桌面验收。

## R3 结构化错误与恢复指引

- 工具业务失败通过标准 MCP tool error 返回，提供稳定 code、安全 message、是否可重试、下一步及已有 Session/Turn/request 引用；不只返回模糊的 connection closed。
- 参数/协议错误遵循 MCP 协议错误语义。初始化前不可避免的进程退出仍向 stderr 提供明确诊断；正常服务设计应将可恢复的下游不可用留到诊断/工具调用阶段。
- 至少区分：Runtime 不可达、授权过期/撤销、身份不匹配、未绑定目标、工作区不匹配、基线变化、Session 忙、准入不确定、幂等载荷冲突、证据不完整和待人工审批。
- “可重试”不等于可以重发副作用。回执丢失先按原 request_id 核对；unknown 不能改为未提交，不能换新 ID 规避不确定性。
- request_id 的相同载荷重试只能指向同一准入；不同载荷必须拒绝。跨重启缺少可信去重/载荷证据时返回不确定，禁止自动重派。
- 不返回 Key、Token、环境变量值、完整私有凭据文件或无关历史；错误不替用户审批、修改基线或清理 Store。

验收：上述故障均能通过稳定类别定位并给出可执行指引；丢失 ACK、重试、重连故障注入均证明最多一次执行准入，无法证明时保守停止。

## R4 按模式暴露工具与兼容性

- 提供明确的 Manual、Reviewer、既有 Managed 工具模式；新接入默认 Manual，避免每次加载全部 Task/Managed 工具。
- Manual 覆盖连接、模型查询、Session 创建/派发、准入核对、按需等待、交接/详细证据和取消。Task 元数据关联按显式配置需要启用，不作为基础委派前提。
- Reviewer 无创建、发送、取消、执行或审批能力；离线证据模式不得使用生产凭据或访问 Daemon。
- Managed 不作为本版默认模式；调用仍受后端 capabilities 和准入约束。
- 保留旧工具名称、参数和返回兼容性及现有 profile 用法；旧配置不能因升级而静默丢失原有工具。默认模式变更只用于新配置，旧模式提供明确兼容路径。
- MCP 的只读 annotation 只是客户端提示；实际权限限制在服务端执行。模式在连接期间稳定，不要求客户端支持动态工具列表才能正确使用。

验收：各模式 tools/list 与允许能力匹配；直接调用隐藏/禁止工具不能绕过权限；已有客户端兼容测试通过。报告工具目录字节数变化，不推算 Codex 额度节省率。

## R5 持久化验证约定与可信 Handoff

- 派发时将验证约定及其版本、关联 request_id/Session/Turn 与准入建立可恢复的一致性关系；返回已准入回执前，必须能够确认验证约定已持久化，或明确返回不确定状态。
- 持久化发生在既有权威存储体系；不能仅写 Bridge 内存、临时文件或以模型总结恢复约定。不为本版建立另一套 Task 数据库。
- 保留原始命令及需要人工/设备完成的检查项；验证规则改动必须版本化，不追溯改写旧 Turn 的通过结论。MCP 不能通过此配置修改模型生成参数。
- Handoff 分离 execution_status、validation_status 和 acceptance_status。completed 不代表测试通过，测试通过不代表用户验收或 Task accepted。
- 检查命令实际状态/退出码、精确事件引用、最后修改之后的验证顺序。管道过滤不能凭末端 exit 0 推断原测试通过；证据不足明确 partial/unknown。
- cancelled/failed 只提供诊断交接；waiting_for_human 是非终态并带 attention 引用，不能伪装为最终交付。
- 默认不传完整历史、Diff 正文或日志；提供按需展开引用。可变工作区证据、冻结 ReviewBundle、已提交版本范围须明确区分，不伪造逐 Turn 快照。
- 旧历史没有验证约定时保持 unknown；不能通过升级补造“已验证”。如无 Task，验收维持独立的人工审查结论，不伪造后端 Accepted。

验收：Bridge 重启后约定及其版本不丢失；准入前后崩溃、事件晚到、重复回执、命令失败、修改后未验证、取消及人工待审批均有负向测试；Handoff 不输出无证据 PASS。

## R6 真实异步交付与故障验收

分层验证：先离线脚本模型和真实 Daemon/SQLite/MCP，再本机只读 GUI，最后单独授权真实任务。不得为了验收绕过原 Store 的 recovery_required 或扩大模型外发范围。

| 场景 | 必须结果 |
| --- | --- |
| 原生接入 | 真实项目 tools/list/调用可用，无临时 stdio 驱动 |
| 一次 Send | 返回稳定 Runtime/Store/Session/Turn/request 准入引用 |
| 提交后退出 | Codex 结束回复；执行期间主动轮询和自动唤醒均为 0 |
| Talkify 观察/审批 | 原 Session 显示执行，用户批准前禁止受保护操作 |
| 返回审查 | 已知有效身份时一次 Handoff 进入审查；必要深入读取有具体原因 |
| MCP 重启/网络失败 | 不改目标、不重派已准入 Turn、不串 cursor；约定可恢复 |
| Daemon 重启 | 明确真实状态；未知副作用不自动重跑，不承诺通用执行恢复 |
| 审批中断 | 非终态或明确失效，不能自动批准或继承失效审批 |
| 授权过期/撤销 | 普通聊天可用，协作拒绝；重新授权不扩大范围 |
| 回执丢失/重复提交 | 同 request_id 核对；不确定时停止，不产生第二个执行 |
| 工作区/Store 切换 | 旧响应不能污染新目标，身份不匹配拒绝 |
| 最终交付 | 约定验证、独立审查、必要人工验收完整；无缺陷可直接 PASS |

记录接入人工步骤、Codex 主动参与轮次、等待调用数、恢复审查调用数、完整工具返回字节、验证完成/缺失项、审批/用户干预、各阶段及总耗时、返工原因和最终交付。区分 Executor 缺验证导致的代劳与必要独立复核。

Code-Agent Provider usage/费用与 Codex 账户使用量分别记录；无法取得时 unknown。不得用合成响应缩减、模型低价格或单次成功推算账户额度节省。一次真实交付只证明流程可用，不证明长期质量/效率收益。

## 实施顺序与发布门槛

1. **V1-a 接入可靠性**：R2 + R3，落实可选服务、错误契约和既有配置迁移说明。
2. **V1-b 绑定与工具模式**：R1 + R4，先完成 schema/并发/授权边界设计评审，再实现及兼容验证。
3. **V1-c 证据持久化**：R5，先评审准入一致性和存储迁移，再实施故障测试。
4. **V1-d 产品验收**：R6，离线及 GUI 通过后，另行确认真实任务、Provider/模型、数据外发范围和预算。

每批提供限定 Diff、测试证据、兼容/迁移及回滚方案；不自动提交、推送、部署或续授权。数据库升级必须保留旧数据及 schema 兼容策略，回滚不能删除新历史或恢复失效凭据。

发布前固定 code-agent、AgentKit、Talkify 兼容版本清单。六项验收通过才标记 Manual Collaboration V1 可发布；Managed 真实模型验收和隔离保障未完成的事实继续明确标示。

本需求不授权模型实验，也不承诺 MCP 能自动结束 Codex 推理；零陪跑依赖客户端指令与实际验收。默认对话可用性由客户端原生设置保证，委派安全由服务端保证。
