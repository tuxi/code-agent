# 后台任务完成通知与执行让出方案

状态：A/B 服务端及 C 阶段的协议与 AgentKit 适配已实现，2026-11-06。完成结果可持久入箱；显式让出后可恢复同一逻辑 Turn 并延续预算。实机多任务、同轮恢复和两种停止路径已核对，配置改为全局默认开启；工作区可显式关闭。双端协商成功且宿主能力齐备后才提供 yield 参数。阶段历史和当前启用规则见第 18 节。

## 1. 要解决的问题

当前后台进程已经可以并行，工具批次也已经支持有界的只读并行。缺少的是：后台工作结束以后，结果如何可靠送回正在执行或已经让出执行的模型。

目前 `run_command(background=true)` 立即返回，`job_wait` 在工具内等待，默认 30 秒、最多 90 秒。`job_finished` 进入事件历史和客户端，但不会成为模型下一步输入。模型容易连续调用 `job_wait`，占用当前 Turn 和调度名额。

目标是让模型继续独立工作，确实需要结果时让出执行，结果到达后继续同一项工作。运行时负责结果交付、身份、预算、取消和执行准入，不推断代码依赖、不替模型安排下一项任务。

本地参考版本：Codex `86ac091659`，OpenCode `fa2843f270`，DeepSeek Harness `fcc0ad4621`。

| 来源 | 采用的原则 | 本次不照搬 |
| --- | --- | --- |
| Codex unified exec | 进程与一次工具调用分离；返回句柄；保留增量输出、退出监听和资源边界 | 不把一次性 Job 改成完整的交互式终端，不引入 PTY/stdin 协议 |

## 3. 收敛决策

1. 保留现有进程注册表、日志子流、独立停止接口和工具名称；P1 编码工具集仍为 22 项。
2. 完成结果是有来源的 Runtime 输入，不是新的人类消息，也不是用户授权。
3. 忙碌的会话在安全的模型请求边界读取通知；不打断正在进行的模型调用或工具批次。
4. 只有模型显式让出的工作可以被后台完成事件自动恢复。单纯看到会话空闲或有 Job 结束，不足以启动模型。
5. 用户正常得到最终答案后，迟到结果保留待下次显式输入，不自动生成另一轮回答。开发服务器、watch 等长期进程不会阻止模型完成。
6. 不增加一个新的“暂停”工具。扩展现有 `job_wait` 的可选参数，旧调用维持原语义。
7. 普通交互编码场景配置默认开启，实际恢复仍要求持久化端口、双端协商及有效的等待身份；用户全局配置或工作区可显式关闭。

## 4. 模型接口：等待与让出是不同操作

现有方式保持兼容：

```json
{"job_id":"job_<opaque-id>","timeout_seconds":30}
```

新方式仅在宿主明确支持 continuation 且工作区开关开启时提供：

```json
{"job_id":"job_<opaque-id>","yield":true}
```

- Job 已结束：立即返回真实终态和有界输出，沿用正常工具流程，不进入等待状态。
- Job 仍运行：立即返回一个结构化让出请求。必须先完成本批次其余调用、补齐所有工具结果并成功保存检查点，随后让出执行。
- `yield:true` 与显式 `timeout_seconds` 不允许同时传入，避免两种语义叠加。
- 一个批次可以让出到多个 Job；任一相关 Job 结束就具备恢复条件，在下一步合并所有已到达结果。不是运行时自动执行依赖图。
- 错误 Job、其他会话的 Job、已失效的来源不得产生恢复请求。
- 用户仍可查看日志或停止指定 Job。停止该 Job 后，真实终态也能解除显式等待，由模型判断后续处理。

提示词在能力真正可用后才调整：先做独立工作；需要结果且没有其他工作时使用让出；禁止忙轮询和重复启动相同工作。保留短时阻塞等待用于兼容，不自动把旧等待改成让出。

## 5. 分层与现有代码的复用

| 层 | 职责与改动边界 |
| --- | --- |
| `internal/jobs` | 仍负责命令、日志、进程组停止和真实终态；不依赖模型或会话调度器 |
| `internal/runtime/jobs_sink.go` | 将真实终态交给持久化通知端口；UI fan-out 与模型通知分别追踪，不在回调中直接启动 Runner |
| Session/SQLite 存储 | 原子记录终态与待交付通知；在检查点事务中追加输入和交付标记；保存让出状态和预算 |
| `internal/conversation` | 持有当前工作身份、等待修订号和停止栅栏；通过既有 TurnScheduler 恢复；取消及恢复竞争在此裁决 |
| `internal/agent` | 通过通用 Runtime 输入/让出接口，在模型边界消费；不检查 `job_wait` 等具体工具名，不导入 jobs 包 |
| AgentKit | 展示“等待后台任务”与恢复状态；不计时轮询后自行发送消息，不承担自动恢复执行权 |

现有 `TurnInputRepository` 是用户提交的持久化入口，不等同于模型每步可消费的收件箱。复用其存储与幂等设计，但不把系统通知塞成新的 `agent_input`。

现有 `ResumeTurn` 面向中断恢复，默认创建新 Turn，且 `drive` 会初始化步数、工具计数、搜索预算与反思状态。不能直接把它作为 Job 完成回调。新增可选的 continuation runner 入口，复用 `drive`，显式恢复保存的执行状态；不支持该入口的第三方 runner 不能启用能力。

Runner 的通用接口应表达“读取待处理 Runtime 输入”“请求让出”“检查最终收尾”，具体类型和名称在实现时随现有接口风格确定。工具返回类型只携带通用控制信号；Job 专属身份校验在工具和 conversation/runtime 适配层完成。

## 6. 结果交付与去重

通知至少包含：`notification_id`、`session_id`、来源 `turn_id/call_id`、`job_id`、终态、真实退出码、耗时、有界输出尾部、创建时间与交付位置。

- 对一个 Job 的终态使用稳定通知 ID 和唯一约束。错误重复回调不会制造第二条待处理结果。
- Job UUID 已在控制接口版本引入，不使用重启后可重用的数字 ID。
- `pending / delivered` 表达模型交付状态；已通过工具得到的结果也记为 delivered，不再重复追加。Job 运行状态保持独立。
- `delivered` 的含义是“输入已原子追加到持久化模型历史”，不声称模型已经理解或远端 API 恰好处理了一次。
- 默认单项输出上限先沿用控制接口的 2000 字节尾部；每步通知整体也设上限，超出继续排队。完整日志通过现有工具获取。
- 多个完成结果在下一次安全边界自然合并，不用额外摘要模型，也不为每个结果各启动一轮。
- 通知中的命令输出是不可信数据，固定包裹为工具来源结果。不能将日志直接放进系统指令。
- Provider 没有专用上下文角色时，在适配层使用兼容的消息角色渲染，但持久来源必须是 Runtime，不能产生人类输入 UI、用户权限或伪造孤立 `tool_call_id`。

若 `job_wait` 已经把终态作为工具结果写入历史，该 Job 的完成通知在同一个检查点事务中标记交付，不再追加一条重复通知。仅拿到 `status:running`、等待超时或读到日志，不算消费终态。

当前 `JobEventSink` 的事件写入是 best-effort，不能据此承诺不丢结果。启用本功能前，SQLite 必须提供终态与通知的原子写入端口；失败时由仍存活的注册表保留结果，执行有界的存储重试并报告错误，不能对模型确认交付。UI 事件已显示不代表模型通知已保存。如果存储持续失败后进程又退出，未落库的结果无法保证恢复，必须退化为“状态无法确认”，不为此引入另一套文件数据库。

事务解决的是本地持久化交付幂等，不承诺跨网络模型请求的 exactly-once。崩溃后历史重发和副作用重做仍遵守既有恢复策略，不能自动重跑原后台命令。

## 7. 忙、闲和让出后的处理

| 所属会话状态 | 到达的终态结果如何处理 |
| --- | --- |
| 正在请求模型 | 入箱，等请求结束；不取消模型请求，也不并发发起第二次请求 |
| 正在执行工具批次 | 入箱，等整个批次工具结果平衡、成功保存后读取 |
| 等待用户审批/提问/计划 | 入箱，不自动批准、不替用户回答；不以 Job 通知绕过挂起原因 |
| 显式 `waiting_background` | 匹配等待身份和修订号后，原子转为可恢复，走既有调度器 |
| 已正常完成但没有显式等待 | 保留通知，下一次用户输入时交付；不自动续写最终答案 |
| 用户已停止 | 保留 Job 真实状态及结果；禁止来源工作的自动恢复 |
| 已归档、已删除、工作区失效 | 拒绝自动恢复，不为通知重新创建会话或绕过已有 in-use 规则 |
| Managed/自动化/跨会话执行域 | 第一版不自动启用；其验收、权限、凭据和预算需要独立适配 |

模型认为可以结束且没有未交付结果时，应允许正常结束，不能仅因为有长期 Job 在运行就强制等待。

最后一次模型调用返回时，还要原子检查收件箱版本：若该调用期间有新结果到达，先保存本次输出为中间正文，再交付新结果进入下一步；若没有，提交终态。终态提交后才到达的结果按空闲规则保留。这样避免“入箱成功却赶不上最后一步”的丢唤醒竞争，也不因为 Job 尚未结束而强行反复请求模型。

## 8. 显式等待的生命周期

新增工作状态 `waiting_background`，与用户取消、应用挂起、模型失败不同。

1. 保存工具批次、执行检查点、等待 Job 集合、模型身份、累计预算和 `wait_revision`，然后发布等待事件。
2. 让出模型/工具执行名额和 TurnScheduler worker，不保留一个阻塞 worker 等进程结束。后台 Job 自身持有的资源租约继续有效。
3. 保留逻辑 Turn 的身份和取消能力；等待不等于完成，不发 `turn_finished`。
4. 完成通知或等待建立时已存在的终态，通过同一事务核对等待修订号，至多安排一个恢复申请。
5. 恢复重新进入既有 TurnScheduler，并再次检查会话、工作区、停止栅栏、权限和凭据；成功后在同一逻辑 Turn 中读取通知继续。
6. 使用原 Turn ID；每次模型调用仍有新 InvocationID。必要的恢复操作 ID 是内部身份，不伪造新用户 Turn，也不重用普通暂停恢复的默认入口。
7. 累计模型步数、工具计数、搜索预算、费用、todo/计划和必要的策略状态必须延续。不能每次唤醒都获得新的 MaxSteps。

等待检查与注册必须是同一个协调操作：先查 Job 再订阅的写法会丢掉两者之间的完成事件。恢复申请也必须是“等待态 + 修订号 + 未停止”的条件更新，不能只靠一个回调布尔值。

## 9. 用户控制、优先级与凭据

- “停止对话”撤销当前逻辑工作的恢复资格，即使当前没有活跃 goroutine。现有 `ActiveTurnRegistry.Cancel` 空闲时直接返回，因此必须补 conversation 层的持久停止栅栏。
- 新能力下的停止请求携带目标 `turn_id`，并核对当前逻辑工作。迟到的旧停止请求不得取消刚提交的新用户工作。旧版不带目标的取消消息保留原有活跃 Turn 语义，不将其扩大成撤销任意历史等待。
- “停止后台任务”仍只停止指定进程。若对话仍在等待，它的取消终态是模型应收到的事实；若对话已停止，不能因此复活。
- 用户新输入优先于旧等待恢复：旧等待原子失效，未消费结果合入新用户工作的输入边界；原后台进程不重复启动。不能在新工作结束后再执行一条排队的旧恢复。
- 明确区分应用挂起、连接断开、用户停止。断线本身不是进程终态，也不是恢复授权；应用后台限制和现有 suspend 策略继续生效。
- 模型沿用来源工作的已解析身份和配置，权限不能提高。凭据仅引用现有安全解析通道，不持久化明文，不在缺失时改用别的账户或默认模型。
- 缺失凭据、连接审批能力不可用或资源准入失败时进入可观察的待恢复/待人工状态，不反复调用模型；通知仍保留。

## 10. 重启与恢复

本版 Job 注册表不跨 daemon 重启，不能从历史 `running` 推断进程仍可访问，也不能重跑原命令。

- 已持久化的终态通知可以在重启后继续交付，但只恢复仍有效的显式等待。
- 未知进程结果显示“状态无法确认”；默认等待用户处理，不伪造成功、失败或取消。
- 交付检查点之前崩溃：通知保持 pending；历史和交付标记同事务，避免保存了消息却没保存消费标记。
- 恢复排队后崩溃：重新校验同一等待修订号和停止栅栏，不能创建第二个恢复申请。
- 用户停止的栅栏必须跨重启有效，不能依赖进程内 cancel context。

## 11. 推进顺序与开启条件

| 阶段 | 实现内容 | 通过条件 |
| --- | --- | --- |
| A：完成结果入箱 | 可选存储端口、SQLite 原子终态/通知、通用 Runtime 输入、忙时安全交付、等待工具结果去重 | 终态与历史落库失败、重复和崩溃窗口测试通过 |
| B：让出及恢复 | `job_wait(yield=true)`、等待检查点、同一逻辑 Turn 的恢复、停止栅栏、用户输入优先、预算延续 | 无双主循环、无丢唤醒、停止后不恢复；普通交互路径集成通过 |
| C：客户端与受控启用 | AgentKit 等待/恢复状态、输入栏停止语义、功能探测和真实 Talkify 验证 | 旧版本兼容，实时/历史一致，真实多任务及停止场景通过 |

实现期间不提前修改默认提示词宣称“会自动通知/恢复”。暂定一个显式工作区开关 `agent.background_job_notifications`，默认 false；最终配置名与既有 settings 合并风格一致。仅完整能力可用时宣告 `background_job_notifications_v1`；缺少持久化端口的 host 不可宣告。已有 `background_job_control_v1` 独立保留，不能拿“能停止任务”代替“能恢复模型”。

暴露 `job_wait(yield=true)` 还要求当前 transport/client 支持等待态和有目标的取消协议；仅服务端宣告能力或工作区开关打开不够。AgentKit 完成双端协商后才启用，CLI/TUI 需要自己的 disposition 适配。旧客户端仍使用原 job_wait；普通暂停恢复接口不能误接收 waiting_background。首次启用时不追认旧版本已启动的 Job，避免把未登记所有者及停止栅栏的历史工作自动续跑。

第一版不做自动依赖推断、自动重试构建、更多并行工具放行、多个主模型同时驱动同一会话、PTY、全局 DAG 或跨进程 Job 恢复。

## 12. 必须覆盖的验收场景

| 场景 | 期望 |
| --- | --- |
| 构建期间读取独立文件 | 读工具正常执行，完成结果在下一安全边界出现 |
| 无独立工作，显式让出 | 不忙轮询，不占 worker，完成后继续同一 Turn |
| 两个 Job 同时结束 | 批量交付，每个终态一条持久输入，最多一个恢复申请 |
| Job 在等待注册前后恰好结束 | 不丢唤醒，也不创建两次恢复 |
| 已通过 job_wait 收到终态 | 不再重复追加完成通知 |
| 用户停止与完成同时发生 | 持久停止栅栏生效后，不能再取得执行许可 |
| 用户新输入与完成同时发生 | 用户输入优先，旧等待恢复失效，结果不丢 |
| 模型返回最终答案时恰好入箱 | 原子决定继续交付或已终结后留待下次，无静默丢失 |
| 来源模型/凭据失效 | 不换账户或模型；保留结果并明确待人工恢复 |
| 审批中、计划中、客户端工具未返回 | 不破坏消息配对，不越过审批边界 |
| 重启、重复事件、落库失败 | 不重跑命令，不恢复用户停止的工作，不声称 exactly-once API |
| 多次让出/恢复 | MaxSteps、搜索、费用和原有计划状态连续累计 |
| 长期开发服务器仍运行 | 模型可以正常结束，不强制无限等待 |
| 旧 AgentKit、旧 host、功能关闭 | 旧 job_wait 兼容，无假能力和新增强制工具 |

## 14. A 阶段已落地范围

## 15. B 阶段已落地范围

- `JobWaitTool.AllowYield` 按 Turn 克隆绑定，只有宿主已授予 continuation 能力、A 阶段开关开启、来源 Job 登记了通知所有者时才提供 `yield`。执行上下文再次核对能力和会话；旧工具 schema、旧阻塞等待、嵌套执行保持兼容。
- 模型显式让出后，先完成整个工具批次，再原子保存历史、等待输入集合和版本化检查点。检查点保留原 Turn ID、模型步数、搜索预算、累计 token/费用、工具计数、计费凭据去重、todo、计划和内置反思状态。最后一个预算步骤不会再让出，沿用一次无工具总结。
- SQLite `runtime_continuations` 记录当前工作、等待修订号和 `active / waiting / ready / stopped / finished / needs_attention`。登记等待和记录结果都在事务内检查另一侧，覆盖“先完成”和“先等待”两种顺序；恢复必须取得匹配修订号的 ready→active 条件更新。
- 让出返回后释放 TurnScheduler、活跃 Turn 和会话操作名额，不保留一个等 Job 的 worker。终态入库后的回调仅是唤醒提示；恢复重新通过既有调度器与执行准入。相同修订号只安排一个恢复申请；两个 Job 结束不会并发驱动同一会话模型。
- `ContinueBackground` 是独立入口，不调用普通 `ResumeTurn`，不补发用户输入或 `turn_started`。原用户 request_id 与逻辑 Turn 保留，每次模型调用仍生成新 InvocationID。新增等待、恢复和待人工处理事件，C 阶段再映射为对外协议与客户端状态。
- 新输入的持久接受事务会撤销旧等待身份；已排队的旧恢复随之取消。旧的 `cancel_turn.turn_id` 不会取消新 Turn。带目标的停止先保存栅栏；等待/排队时的取消事件、累计统计和会话状态同事务提交，再分发已有事件行。
- 活跃 Turn 的身份核对与取消在注册表同一把锁内完成，不采用“读调度快照再按会话取消”的有竞争写法。恢复准入的落库失败通过错误回调或日志报告，保持待处理状态，不静默调用模型。
- 不带 turn_id 的旧取消保持活跃 Turn 语义；携带空、null、无效或旧 turn_id 的消息不会退化为“取消当前新对话”。不支持有目标取消的旧 CommandTarget 也不会被误调用旧 Cancel。
- 恢复前检查会话、归档、工作区绑定、执行租约、当前连接、模型配置、凭据来源与可识别作用域、权限层级和规则指纹。变化或缺失进入 needs_attention，不切换模型/账户、不忙重试。会话注入凭据若无法提供稳定作用域，首版不授予让出能力。未知的有状态 StopPolicy 同样不开放，避免重置策略状态。
- `SetBackgroundContinuationSupport` 是宿主内部入口，生产 transport 尚不调用。C 阶段必须在双端协商完成后授予，并在断开/挂起时撤销。断开或应用挂起中断恢复时保留暂停/待处理语义，不伪造用户停止。
- 已持久化的 ready 检查点可以由重新连接且身份匹配的宿主继续；普通恢复接口不会接管等待工作。缺少已保存终态的旧进程不自动启动模型，也不重跑命令。恢复执行中崩溃或中断后的不确定状态留待人工处理，不通过普通 Resume 刷新预算。
- daemon 与 embedded 两个装配入口均已接入完成回调；没有修改 AgentKit、实际用户配置或能力宣告。受控端到端测试验证真实后台进程经 Serve 构建器启动、让出、取消产生终态、原 Turn 恢复和最终回答；不是 Talkify 的验收结论。
